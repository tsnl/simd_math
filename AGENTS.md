# AGENTS.md

This file provides guidance to AI coding agents (Claude Code reads it via the CLAUDE.md symlink) when working with code in this repository.

## Overview

`simd_math` is a Rust library crate (published to crates.io) providing SIMD-accelerated vector, quaternion, affine-matrix, transform, and AABB math for games, graphics, and robotics. It is built on `std::simd` (`#![feature(portable_simd)]`), so it **requires nightly Rust** — the toolchain is pinned in `rust-toolchain.toml` and picked up automatically by cargo/rustup. `portable_simd` is still unstable with no announced stabilization date, so the pin is a long-term posture, not a temporary workaround.

## Commands

```sh
cargo test                          # run all tests (unit + integration + doctests)
cargo test test_name                # run a single test by name
cargo test --test integration_test  # run only tests/integration_test.rs
cargo clippy --all-targets -- -D warnings   # lint; CI fails on any warning
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps   # docs must be warning-free
cargo fmt -- --check                # check formatting (CI-enforced); drop --check to fix
cargo bench                         # micro-benchmarks with scalar baselines
```

CI (`.github/workflows/ci.yml`) runs three jobs — Test, Lint, and Check Formatting — and all must pass. Lint covers both clippy (`--all-targets`, so tests and benches are linted too) and the rustdoc warning check. `cargo bench` is not run in CI.

`rust-toolchain.toml` is the single source of truth for the toolchain: both workflows install from it rather than naming a version, so bumping the nightly there updates CI and publish together.

Releases are made via the manually-dispatched Publish workflow, which bumps the version in `Cargo.toml`, tags, and publishes to crates.io. Do not hand-bump the version as part of ordinary changes. It defaults to a dry run; choose the bump type deliberately, since the crate is past 1.0 and breaking changes need a major bump.

## Architecture

All modules (`vector`, `quaternion`, `mat3x4`, `transform`, `rect`) are re-exported flat from `src/lib.rs`, so everything is `simd_math::TypeName`. `simd_math::prelude` re-exports every public type plus the component-index constants `X`/`Y`/`Z`/`W`.

**Newtype-over-SIMD pattern.** Every type wraps a `std::simd` vector (e.g. `SimdVec3(pub(crate) f32x4)`). The inner `.0` field is `pub(crate)`, so cross-module code inside the crate manipulates raw SIMD lanes directly; the public API never exposes it (no `std::simd` types appear in public signatures).

**Padding-lane invariant.** 3-lane types are backed by 4-lane SIMD vectors (`SimdVec3` = `f32x4`, `SimdIVec3`/`SimdUVec3` likewise) with the fourth lane **always zero in every stored value**. This is load-bearing, not incidental: `SimdMat3x4`'s matmul relies on each column's hidden W lane being 0. Any new operation must preserve it.

Consequences to respect when adding code:

- Constructors (including `splat`) must zero the pad lane.
- `PartialEq` is hand-written to compare only the visible lanes — do **not** re-derive it. `PartialOrd` is deliberately absent (lexicographic ordering over SIMD lanes is not meaningful), and `Debug` prints only the visible lanes.
- `Index`/`IndexMut` assert `index < dim`, so `v[3]` on a `SimdVec3` panics rather than exposing the pad lane.
- Where zero is not a neutral element (elementwise division, product reduction), use the private `with_padding_ones` helper to build a **temporary** operand register. Never store or return such a register — that would break the invariant above.

**Macro-generated impls in tiers.** Vector types and their trait impls are generated by macros in `src/vector.rs` with three tiers: `impl_uint_simd_vec!` (basic ops) → `impl_int_simd_vec!` (adds `Neg`) → `impl_float_simd_vec!` (adds norm/normalize/lerp/clamp/powf). Rect types (`SimdRect2/3`, `SimdIRect2/3`, `SimdURect2/3`) are likewise generated by `impl_simd_rect!` in `src/rect.rs`. To add a method across all vector or rect types, extend the appropriate macro, not individual impls.

**Key type semantics:**
- `SimdUnitQuat` is stored as `(s, x, y, z)` and is *always* unit-norm — constructors normalize and panic on un-normalizable input, and `inverse()` relies on this (it is just the conjugate). Preserve this invariant in any new constructor. Rotation of a vector uses the two-cross-product sandwich form, not two quaternion multiplications.
- `SimdMat3x4` is a 3×4 affine matrix: four `SimdVec3` columns (three transformed basis vectors + translation), with an implicit `[0, 0, 0, 1]` bottom row. It is not a general 4×4 matrix. It maps homogeneous 4-vectors to 3-vectors; `Mul<SimdVec4>` treats W as the translation coefficient (W=1 point, W=0 direction) and preserves W in the output.
- `SimdTransform` is position + rotation only (no scale), so it composes and inverts more cheaply than `SimdMat3x4` and cannot drift away from being rigid.
- Rects are min/max AABBs with **inclusive** bounds; union uses the `|`/`|=` operators (with vectors or rects), intersection uses `&`/`&=`, with `union_identity()`/`intersection_identity()` as fold seeds. Prefer the `contains`/`intersects`/`is_empty` predicates over hand-rolled per-component comparisons. `center()` is computed as `min + extent/2` so integer rects cannot overflow.

**Conventions (from README.md):** arrays are the interchange format (`From<[T; N]>` both ways); there are no `.x`/`.y`/`.z` accessors — use indexing, either `v[0]` or `v[X]` with the prelude constants; vectors are column vectors and multiplication is `Matrix * Vector`; matrices are constructed column-major (each constructor argument is a column) and their dimensions are named **rows×columns** as in mathematics, HLSL, and Vulkan (GLSL/GLM name them columns-first and would call this same shape `mat4x3`); right-handed coordinate system; spherical coordinates are `(azimuth, elevation, radius)` with Y up.

`#![warn(missing_docs)]` is enabled and CI treats warnings as errors, so **every new public item needs a doc comment**. Pure methods should carry `#[must_use]`, matching the existing code.

## Tests

Unit tests live inline in each `src/*.rs` file and are themselves macro-generated per type (e.g. `test_simd_vec_float_methods!` in `src/vector.rs`) — extend the test macros when extending the impl macros. `src/vector.rs` also has a dedicated `padding_lane_tests` module guarding the invariant above; add to it when you add an operation that touches lanes.

Broader behavioral tests live in `tests/integration_test.rs`; its `test_readme_example()` mirrors the README code example, so keep the two in sync when either changes. Prefer asserting exact expected values over loose qualitative bounds — several tests were tightened from `assert!(x.norm() > 0.99)`-style checks to exact comparisons, and the loose form has hidden real bugs here before.
